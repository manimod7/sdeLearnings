🔍 1. What is Debezium?

Debezium is an open-source distributed Change Data Capture (CDC) platform. It's built on top of Apache Kafka and Kafka Connect to stream real-time changes from your database into Kafka topics.

It allows downstream applications, services, or event processors to consume and react to insert/update/delete events without querying the database over and over again.

Think of Debezium as a way to treat your traditional database as a stream of events.

🔄 2. Understanding Change Data Capture (CDC)

Change Data Capture (CDC) is a design pattern that captures changes in a database (INSERT, UPDATE, DELETE) and delivers them to other systems or services in real-time or near-real-time.

Traditional systems use polling, batch loads (like ETL), or application-level callbacks — but these have drawbacks such as stale data, missing events, and increased coupling.

Log-based CDC (used by Debezium) reads from the append-only write-ahead logs (WAL, binlogs) of databases to provide an accurate, low-latency change stream.

Benefits of CDC:

  • 📥 Keeps systems synchronized in real-time
  • 📤 Publishes events with little-to-no overhead
  • ⚡ Allows event-driven architectures without touching app code

📂 3. Supported Databases

Debezium supports multiple relational and some NoSQL databases. A connector is a Kafka Connect plugin that reads data changes from a specific database type.

Database Status CDC Mechanism
MySQL / MariaDB ✅ Stable Binlog
PostgreSQL ✅ Stable WAL (Logical Replication)
MongoDB ✅ Stable Oplog
SQL Server ✅ Stable Transaction Log
Oracle ✅ Stable LogMiner/XStream
Db2 ✅ Stable Database Journal
Vitess / Spanner ⚠️ Incubating Tablet binary logs / CDC

Connectors are shipped as Kafka Connect plugins, and each database type requires a specific set of permissions and log configurations.

⚙️ 4. How Debezium Works

Debezium connectors run inside Kafka Connect (either distributed or standalone). Each connector instance:

  1. Connects to the database and performs an optional initial snapshot (creates baseline if no offset exists)
  2. Begins tailing the write-ahead transaction log of the source DB
  3. For each change in the log, emits a change event in JSON (or Avro, or Protobuf)
  4. Writes the event to a Kafka topic like db.server1.inventory.products
  5. Consumers can subscribe to these Kafka topics and react accordingly.

Here's what a Kafka change event might look like (for PostgreSQL):

{
  "before": { "id": 1, "name": "old", "price": 100 },
  "after":  { "id": 1, "name": "new", "price": 150 },
  "source": { "db": "sales", "ts_ms": 1710000000000 },
  "op": "u",   // operation: c=create, u=update, d=delete
  "ts_ms": 1710000001000
}

Each connector maintains internal offsets and resume points via Kafka. This allows:

  • High availability and crash recovery
  • Offset checkpointing across Kafka partitions
  • Replay of changes by rewinding Kafka offsets
